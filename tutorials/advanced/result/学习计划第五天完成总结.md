## 2. 核心概念与公式

### 2.1 布隆过滤器原理

- 布隆过滤器是一种空间高效的概率型数据结构，用于判断元素是否“可能存在”；返回 `false` 表示元素一定不存在，返回 `true` 表示可能存在（有一定概率的误报）。
- 误报率由位数组大小 `m`、哈希函数数量 `k`、元素数量 `n` 决定；通过最优化可得公式：`m = -n * ln(p) / (ln2)^2`，`k = (m/n) * ln2`。
- 在 LSM Tree 的查询流程中，布隆过滤器可在读取 SSTable 前进行“存在性预判”，显著减少不必要的磁盘 I/O。

### 2.2 项目实现要点（代码对应）

- 位数组大小与哈希函数个数计算：`BloomFilter.java:14-21`（计算 `size` 与 `hashFunctions`）
- 元素添加与存在性判断：`BloomFilter.java:26-46`

## 4. 测试与性能分析

### 4.1 功能测试

- 正确性：添加与查询匹配（`BloomFilter.add` / `BloomFilter.mightContain`）行为正常；SSTable 查询路径在布隆过滤器判定为“不可能存在”时不进行磁盘扫描。
- 兼容性：Double Hashing 避免实现多个独立哈希函数，降低实现复杂度并保证分布性（来源：Bloom filter 常用实现策略）。

### 4.2 计算与空间开销（基于公式的数据来源）

- 设 `n = 100000`、`p = 0.01`：
  - 位数组大小 `m ≈ 958,505 bit ≈ 117 KB`（公式来源 Wikipedia/Broder & Mitzenmacher）
  - 哈希函数数量 `k ≈ 7`（四舍五入）
- 相比不使用过滤器，布隆过滤器在大多数不存在键的查询上可避免磁盘 I/O；避免比例依赖键分布与多层 SSTable 命中概率（来源：LSM Tree 查询流程）。

### 4.3 项目表现与建议

- 当前实现在每次加载现有 SSTable 时重建布隆过滤器（`SSTable.java:47-59`）；对于大量文件，建议持久化 Bloom Filter 并在加载时直接恢复（减少首次启动扫描成本）。
- `BloomFilter.fromByteArray(...)` 仍为占位实现，未严格恢复 `size/hashFunctions` 配置（`BloomFilter.java:68-74`）；建议完善持久化格式与恢复逻辑以确保一致的误报率。

## 5. 技术深度分析与优化方向

### 5.1 误报率与性能权衡

- 较低误报率需要更大的 `m` 与更多的 `k`，会增加内存占用与 CPU 哈希计算开销；在 SSD/NVMe 环境中，建议 `p` 取 1%~2% 以在命中率与 CPU 消耗之间取得平衡（来源：常见工程实践）。

### 5.2 工程改进建议（结合项目）

- 持久化 Bloom Filter：在 SSTable 写入时序列化位数组与参数（`m/k`），加载时直接恢复，避免 `rebuildBloomFilter` 顺序扫描（建议新增头部区段或伴随文件）。
- 分层 Bloom Filter：为每层 SSTable 维护聚合过滤器；在多层查询时先按层过滤再逐表过滤，减少跨层扫描。
- 与缓存协同：结合 Row Cache/Block Cache，在布隆过滤判定后优先查询缓存，再决定是否读取磁盘（参考项目缓存模块）。
