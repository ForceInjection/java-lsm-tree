## 2. LSM Tree 架构核心概念与来源说明

### 2.1 核心概念

#### 2.1.1 架构设计要点（来源均为业界权威资料）

- **分层存储架构**：LSM Tree 采用内存+磁盘的分层设计，MemTable 处理热数据，SSTable 存储冷数据
- **组件协调机制**：WAL、MemTable、SSTable、压缩策略等组件需要精确协调工作
- **并发控制模式**：读写锁（ReadWriteLock）确保读写并发安全，写操作互斥，读操作可并发

#### 2.1.2 参考资料（可直接检索验证）

- O'Neil, Cheng, Gawlick, O'Neil. "The Log-Structured Merge-Tree (LSM-Tree)". Acta Informatica, 1996.
- RocksDB Architecture Guide: [RocksDB Architecture](https://github.com/facebook/rocksdb/wiki/RocksDB-Architecture-Guide)
- Java Concurrency in Practice. Brian Goetz et al. Addison-Wesley, 2006.

### 3.2 并发控制机制

#### 3.2.1 读写锁应用

- **写操作锁**：`put()` 和 `delete()` 方法使用写锁（`LSMTree.java:100,133`）
- **读操作锁**：`get()` 方法使用读锁（`LSMTree.java:165`）
- **锁范围**：精确控制锁粒度，避免长时间持有锁

#### 3.2.2 写入路径并发控制

```java
public void put(String key, String value) throws IOException {
    lock.writeLock().lock();  // 获取写锁
    try {
        wal.append(WriteAheadLog.LogEntry.put(key, value));  // 先写WAL
        activeMemTable.put(key, value);  // 再写MemTable
        if (activeMemTable.shouldFlush()) {
            flushMemTable();  // MemTable刷盘
        }
    } finally {
        lock.writeLock().unlock();  // 释放写锁
    }
}
```

public String get(String key) {
    lock.readLock().lock();  // 获取读锁
    try {
        // 查询缓存 → 活跃MemTable → 不可变MemTable → SSTable
        KeyValue ent = activeMemTable.getEntry(key);
        if (ent != null) return ent.getValue();
        // ... 继续查询其他组件
    } finally {
        lock.readLock().unlock();  // 释放读锁

### 3.3 组件协调机制

#### 3.3.1 写入流程协调

1. **WAL 优先**：所有修改先追加到 WAL 确保持久性（`LSMTree.java:102-103`）
2. **MemTable 更新**：写入活跃 MemTable（`LSMTree.java:105-106`）
3. **刷盘检查**：检查 MemTable 是否达到刷盘阈值（`LSMTree.java:108-111`）
4. **缓存更新**：更新缓存系统（如果配置）（`LSMTree.java:112-117`）

#### 3.3.2 查询流程协调

1. **缓存查询**：优先查询缓存系统（`LSMTree.java:167-176`）
2. **MemTable 查询**：查询活跃 MemTable（`LSMTree.java:177-185`）
3. **不可变 MemTable 查询**：按时间倒序查询不可变 MemTable（`LSMTree.java:187-198`）
4. **SSTable 查询**：最后查询磁盘上的 SSTable 文件

#### 3.3.3 后台压缩协调

- **异步执行**：压缩任务在后台线程执行，不影响前台操作（`LSMTree.java:71-76`）
- **锁协调**：压缩时需要获取写锁，确保数据一致性
- **资源管理**：合理的线程池配置和资源清理

## 5. 性能分析与优化建议

### 5.1 并发性能分析

#### 5.1.1 读写锁性能特征

- **读多写少**场景：读写锁提供优秀的并发性能
- **写密集型**场景：写锁可能成为瓶颈
- **锁粒度**：当前实现采用粗粒度锁，可考虑细粒度优化

#### 5.1.2 性能瓶颈识别

- **写锁竞争**：高并发写入时的锁等待
- **MemTable 刷盘**：刷盘操作阻塞写操作
- **压缩影响**：后台压缩对前台操作的影响

### 5.2 优化建议

#### 5.2.1 并发优化

- **锁分离**：将锁按组件或功能进行分离
- **无锁数据结构**：在适当场景使用无锁或乐观锁
- **异步处理**：将非关键路径操作异步化

#### 5.2.2 架构优化

- **多 MemTable 设计**：支持多个活跃 MemTable 减少锁竞争
- **分层锁机制**：不同组件使用不同的锁策略
- **压缩调度优化**：智能调度压缩任务避免高峰期

#### 5.2.3 监控优化

- **细粒度监控**：监控每个组件的性能指标
- **锁监控**：详细监控锁竞争情况和等待时间
- **预警机制**：设置性能阈值预警
